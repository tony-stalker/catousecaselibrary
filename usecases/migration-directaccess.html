Microsoft DirectAccess to Cato

Microsoft has deprecated DirectAccess and will remove it from a future Windows Server release — so every estate still running it has to move anyway. This is the focused remote-access play: replace DirectAccess and the infrastructure that keeps it alive — the Network Location Server, the PKI, the IP-HTTPS gateway and the Group Policy plumbing — with the Cato Client and SDP. Always-on like DirectAccess, but cross-platform, no domain-join requirement, with device posture, IdP MFA and app-level least privilege enforced at the nearest PoP, and nothing left to keep alive.

Business objective

The forced decision point

Microsoft has made the decision for you. Its guidance is unambiguous: "DirectAccess has been deprecated and will be removed in a future version of Windows Server," and it "highly recommends that you use Always On VPN instead of DirectAccess for new deployments." DirectAccess still ships and still functions in Windows Server 2025 and other supported releases — but it is on the removal path, and the countdown is your Windows Server refresh cycle. When the estate moves to a release without DirectAccess, remote access stops being a feature you can renew.

So the question is not whether to run this project — it is what you land on. Microsoft's in-place successor, Always On VPN, is the sanctioned Windows path, but it is still a VPN gateway estate you build and operate yourself: RRAS gateways, NPS/RADIUS, a certificate authority, HA pairs. DirectAccess had deeper structural limits than any of that fixes. It is Windows-only and domain-joined-only — Microsoft states it "provides support only for domain-joined clients," and only on Enterprise editions of Windows, so Macs, phones, tablets and contractor laptops were never covered. It is transparent but fragile: the Network Location Server is a single point of failure, IP-HTTPS carries a performance cost, and the whole thing rests on a PKI and Group Policy estate that has to be renewed and nursed. And it grants network-level access, not least-privilege ZTNA.

Cato SDP inverts the model. The Cato Client is always-on like DirectAccess, but it runs on Windows, macOS and mobile, needs no domain join, authenticates through your IdP with SSO and MFA, and checks device posture continuously. It terminates at the nearest of Cato's PoPs — where the full security stack is enforced in the cloud — and reaches datacentre and cloud applications directly over the global private backbone, at the level of the named application rather than the subnet. There is no NLS, no PKI estate, no IP-HTTPS gateway to keep alive. Same forced migration, fundamentally better end state.

A deprecation with a moving deadline

DirectAccess is deprecated today and remains available in Windows Server 2025, so it is easy to defer. But it will be removed from a future release, and the trigger is your own server-estate refresh — not a date you control. Planning the move now is cheaper than discovering the feature is gone during an OS upgrade.

The Windows-only, domain-joined ceiling

DirectAccess supports only domain-joined clients on Enterprise editions of Windows. Every Mac, every phone, every tablet and every contractor or BYOD laptop sits outside it — served, if at all, by a second remote-access tool. The population DirectAccess never reached is exactly the one that has grown.

Transparent, but fragile

The Network Location Server tells the client whether it is inside or outside the network — and when it is unreachable, clients misjudge their location and connectivity breaks, which makes it a single point of failure. IP-HTTPS, the fallback that tunnels through firewalls, adds an encryption overhead; and the PKI and GPO estate underneath all needs renewing and nursing.

Network access, not least privilege

DirectAccess connects the machine to the corporate network — full intranet reach governed by whatever firewall rules kept pace. There is no per-application gate and no continuous device-posture decision. Once the tunnel is up, lateral reach is the network's, not the policy's.

Discovery questions

How many non-Windows and unmanaged users are unserved by DirectAccess today — Macs, phones, contractors — and what tool covers them instead? What happens to remote clients when the NLS is down? Who owns the certificate authority and the renewal calendar? And which Windows Server release in your estate is the one that finally forces the change?

The Cato solution

From DA gateway to nearest PoP

The Cato Client is a lightweight, always-on agent that connects each user to the nearest Cato PoP, authenticating through your IdP (Entra ID, Okta, OneLogin — multiple IdPs supported) with SSO and MFA, and evaluating device posture continuously throughout the session rather than only at connect. From the PoP, traffic to private applications rides the global private backbone to the datacentre Socket; internet and SaaS traffic breaks out through the same inspection stack that protects sites. There is no DirectAccess gateway, no Network Location Server, no certificate authority dedicated to remote access and no IP-HTTPS listener — nothing to size, renew or nurse.

The migration path

Six steps from DirectAccess to SDP

The sequencing below follows Cato's recommended practice for always-on client migrations: build the Cato side first, move cohorts cleanly, and keep the DirectAccess gateway warm until the last wave clears — then decommission the plumbing deliberately.

  1. Discover & inventory

    Map what DirectAccess actually encodes: the client GPOs that push the configuration, the Network Location Server, the certificate authority and certificate templates it depends on, the IP-HTTPS gateway, and the DA server roles. Confirm who is in scope — and explicitly capture the users DirectAccess never covered: Mac, mobile, unmanaged and contractor. That non-Windows population is part of the target from the start, not an afterthought.

  2. Build the Cato side

    Access → Device Posture Access → Client Connectivity Policy

    Connect the IdP with SSO and SCIM provisioning so users and groups stay in sync. Recreate the "managed corporate device" intent as Device Posture profiles — certificate present, disk encryption, anti-malware, OS version, domain membership where wanted — and run them in monitor first. Build the Client Connectivity Policy (who may connect, from where, on what device) and the app-level access rules that replace network-level intranet reach.

  3. Pilot cohort — swap, don't stack

    DirectAccess installs its own VPN tunnel adapter, and it does not tolerate a second always-on tunnel beside it: leave DirectAccess and the Cato Client both active on one device and their adapters and routing tables fight, producing intermittent, hard-to-diagnose connectivity. So the pilot is a per-device swap, not a parallel run — remove the DirectAccess client configuration for the device (GPO / unenrol) so its tunnel adapter tears down, then the Cato Client becomes the sole tunnel. Validate on that device: always-on connects, every in-scope application is reachable, and posture verdicts are correct before you widen the ring.

  4. Wave rollout

    Roll cohorts by department or region. For each, remove the DirectAccess client GPO (or unenrol the device) so the Cato Client becomes the primary path, and run the same acceptance checklist. Crucially, extend each wave to the Mac, mobile and contractor users DirectAccess never reached — the same policy now covers the whole workforce, not just domain-joined Windows.

  5. Decommission the plumbing

    Once the last cohort is off, retire the DirectAccess gateway, the Network Location Server and the IP-HTTPS listener, and release the certificate-authority role and templates dedicated to remote access. Re-point anything externally keyed to the DA egress addresses as part of the wave plan. This is the estate DirectAccess needed that now simply disappears.

  6. Optimise

    Monitor → Events

    Flip Device Posture from monitor to enforce, keep always-on so users are protected before they think about connecting, and tighten access from network-level reach to app-level rules using real traffic evidence from Events. This is where the estate ends up ahead of where an Always On VPN rebuild would have left it — cross-platform, posture-aware and least-privilege.

Co-existence & rollback

Cohort mechanics, GPO as the lever

Client migrations co-exist by cohort, not on the device. At any moment during the rollout some users run DirectAccess and some run the Cato Client — but never both on the same endpoint at the same time: their tunnel adapters conflict and the user gets unpredictable connectivity. The swap is therefore atomic per device, and the lever that moves a cohort — and the lever that rolls it back — is the same: the DirectAccess client GPO.

One tunnel at a time

Do not run DirectAccess and the Cato Client together on one device — the two always-on tunnel adapters clash and produce intermittent, hard-to-diagnose behaviour. Removing the DirectAccess client configuration must happen as the Cato Client takes over, not after.

Cohort mechanics

Cohorts follow deployment rings: pilot → early adopters → departmental waves. Per device, remove the DirectAccess GPO so its tunnel adapter tears down as the Cato Client takes over as the sole tunnel — never both at once — with a per-cohort acceptance checklist of the apps that cohort actually uses.

GPO revert = rollback

Rollback is mechanical and per cohort: re-apply the DirectAccess client GPO and the device is back on the old path at next policy refresh. Because the DA gateway stays up until the final wave, the known-good route is always there to fall back to.

Keep the gateway warm

Rollback stays cheap only while the old path exists. Keep the DirectAccess gateway, the NLS and the CA running and monitored until the last cohort completes its soak window — then decommission deliberately, not opportunistically.

Rollback rule

Do not retire the Network Location Server, the certificate authority or the IP-HTTPS gateway until the final cohort has cleared. They are the fallback path; pulling them early turns a routine rollback into an incident.

Demo runbook

How to run the demo

Before you demo

Anchor on their trigger: is it the DirectAccess deprecation notice, a Windows Server upgrade that forces the question, an NLS outage that broke remote users, or the Mac and mobile population DirectAccess never served? Run the demo as "the move you already have to make — made once, properly, and to more than Windows".

  1. Connect with the Cato Client

    Connect as a demo user — SSO and MFA at the IdP — and show the client attach to the nearest PoP, always-on. Make the contrast explicit: no NLS deciding whether the client thinks it is inside or outside, no IP-HTTPS fallback, no domain-join prerequisite. Then note it is the same client on macOS and mobile.

  2. Show the connection gate

    Access → Client Connectivity Policy

    Walk the rules that decide who may establish a session at all — user group, country, device posture profile. This is the control DirectAccess expressed as GPO scoping and security-group membership, made explicit and identity-driven.

  3. Open a Device Posture profile

    Access → Device Posture

    Show the checks — certificate, disk encryption, anti-malware, OS version, client version — and make the point that they are evaluated continuously during the session, not assumed from domain membership at connect. This is the "managed device" assurance DirectAccess implied, turned into an enforced, live decision.

  4. App-level access vs network access

    Security → WAN Firewall

    Show a rule granting a user group one named application in the datacentre — and the absence of any rule granting the whole subnet. Then show the same user blocked from an adjacent resource. DirectAccess put the machine on the network; Cato puts the user on the application.

  5. Close on the session trail

    Monitor → Events

    Filter events to the demo user: connection, posture verdicts, every allow and block, fully attributed to identity. This is the audit trail a DirectAccess deployment — spread across the DA server, NLS and event logs — never quite delivered in one place.

PoV runbook

How to prove it in the customer's tenant

This PoV is a swap-don't-stack retirement pilot: a cohort of 10–15 real DirectAccess devices moved cleanly to the Cato Client, one at a time, while the rest of the DA estate carries on untouched. Because the two always-on tunnel adapters clash on a shared device, the swap procedure is not plumbing — it is success criterion number one. Prerequisites — agree before week one
  • Licences — ZTNA/SDP user licences covering the cohort for the PoV period.
  • Identity first — IdP connected and a dedicated pilot group (e.g. DA-Pilot) provisioning via SCIM before any policy is written (SCIM User Provisioning).
  • Levers ready on both sides — the DirectAccess client GPO scoped by a security group, so removing a device is a membership change rather than a GPO edit; and the Cato Client package staged in the same GPO/MDM estate that pushed DA config (Distributing Cato Clients to Devices).
  • Apps reachable via Cato — the datacentre resources DA publishes must sit behind a Cato Socket before the first swap, or the first swapped user proves the wrong thing.
  • Cohort composition — mostly domain-joined Windows laptops (the DA population), plus at least one macOS or mobile user for the ceiling-lifted criterion. Note Always-On does not cover Linux — keep Linux devices out of the parity criterion.

Configuration walkthrough

  1. Pin the cohort in identity

    Access → Directory Services Access → Users

    Scope SCIM provisioning to the DA-Pilot group and confirm its members appear under Access → Users. Every Cato policy in this PoV references the synced group — joiners and leavers maintain themselves, which is already an improvement on the security-group-plus-GPO scoping DirectAccess used (SCIM User Provisioning).

  2. Make the implied trust explicit

    Access → Device Posture

    DirectAccess inferred "managed device" from domain join at connect. Recreate that assurance as posture: a device certificate check plus a disk encryption check, bundled into a profile (e.g. DA-Pilot-Managed) — checks inside a profile combine with AND, so the device must satisfy every one. Keep platform support in mind from the start: some checks are platform-specific, which matters for the macOS cohort member (Creating Device Posture Profiles and Device Checks).

  3. Gate the connection — monitor-first

    Access → Client Connectivity Policy

    Week-one rule: source DA-Pilot, platforms in scope, Device Posture Profile Any, action Allow WAN and Internet. The policy is ordered first-match and ends in an implicit any-any block, so the pilot rule must sit where it actually catches the cohort. Posture is not enforced yet — a clean week of connection events is the baseline that makes the enforcement flip in step 7 meaningful (Configuring the Client Connectivity Policy).

  4. Replace subnet reach with named applications

    Security → WAN Firewall

    From the discovery inventory, list what the cohort actually uses over DirectAccess — it is nearly always shorter than anyone expects — and write one WAN Firewall rule per named application, source DA-Pilot. Deliberately leave one adjacent resource unmatched: the block event it generates later is the least-privilege evidence artefact. DirectAccess put the machine on the network; this rulebase puts the user on the application.

  5. Execute the swap — criterion one, per device, in order

    Monitor → Events

    The adapter clash makes coexistence a non-option, so the order is non-negotiable: remove the device from the DA GPO scope group → reboot (computer group membership applies at next boot) → verify the DA client config is gone → push the Cato Client → sign in with IdP SSO and MFA. Verify before installing, on every device:

    # after reboot, before the Cato Client goes on
gpupdate /force
gpresult /r            # DA client GPO must no longer be listed
netsh namespace show effectivepolicy   # NRPT must be empty — no DA name-resolution rules

    The first connected event for the device in Monitor → Events, timestamped after the verification, closes that device's row on the runsheet.

  6. Enforce always-on — the parity proof

    Access → Always-On Policy

    Add a rule for DA-Pilot so the cohort stays connected to the Cato Cloud without user action — the property DA users will miss if it is absent, delivered without the NLS. Bypass is governed, not hidden: an admin-issued one-time passcode valid for up to 15 minutes, and a user-initiated bypass with a recorded reason on the Windows and macOS Clients and iOS 5.6+ (Windows 5.9+ also sets how long a bypass lasts). Have a cohort member try to disconnect without one — that refusal screenshot is a success-criterion artefact (Protecting Users with Always-On Security).

  7. Turn the posture key, then baseline the fortnight

    Access → Client Connectivity Policy Home → Experience Monitoring

    After the clean week, edit the connection rule to require DA-Pilot-Managed — the domain-join assumption is now an enforced, continuous decision. Then let the cohort live on it, capturing the Remote Users tab of Experience Monitoring weekly: per-user experience score, connected PoP, flows and average TTFB. The macOS or mobile member's row in that same table, under the same policy, is the ceiling-lifted evidence in one screenshot (Using the Experience Monitoring Page).

  8. Run the rollback drill — deliberately

    Mid-pilot, pick one device and reverse it: remove the Cato Client first, then re-add the device to the DA GPO scope group and reboot — the same one-tunnel rule applied backwards. At the next policy refresh the device is on DirectAccess again, because the NLS, PKI and IP-HTTPS gateway were never touched. Rollback proven cheap is what lets the customer sign off wave rollouts with confidence — it is the criterion that de-risks all the others.

What good output looks like

Troubleshooting the pilot

⚡

Intermittent connectivity right after a swap

The signature of both tunnels alive at once. Run gpresult /r and netsh namespace show effectivepolicy on the device — if the DA client GPO or NRPT rules are still present, the removal never took. Pull the device from the DA scope group, reboot, verify clean, and only then let the Cato Client run.

🔁

GPO removal that never lands

Computer group membership changes only apply after a reboot — a swap runsheet without the reboot step leaves DirectAccess active underneath the new client. If a device keeps re-acquiring DA config, check for a second GPO link or WMI filter still scoping it in.

⏳

SCIM sync lag

A cohort member cannot connect or misses every rule. Check membership under Access → Users and the IdP provisioning log — push cycles are not instant. Trigger on-demand provisioning from the IdP rather than re-editing Cato policy to compensate.

🍏

Posture fails the macOS member

A profile built around Windows-issued device certificates cannot pass on a Mac. Scope checks by platform — some check types are platform-specific — and prove the macOS user against the checks their platform supports. This is exactly the conversation DirectAccess never let you have.

🚫

Pilot user hits the implicit block

The client signs in but access is refused and no rule matched. The Client Connectivity Policy is first-match and ends in an implicit any-any block — confirm the user is in the synced DA-Pilot group and the pilot rule sits above any narrower rule stealing the match.

🧊

Non-pilot DA users break mid-PoV

Almost always someone "tidying" DA infrastructure early — an NLS certificate allowed to lapse, a CRL endpoint moved, an IP-HTTPS listener re-addressed. Freeze all change on the NLS, PKI and gateway for the pilot window; the untouched-estate criterion exists to catch exactly this.

Gotchas & exit

Say these out loud before week one
  • The swap is atomic per device. Never schedule the Cato Client push before DA removal is verified on that device — the adapter clash produces intermittent, hard-to-diagnose behaviour, which is the worst possible evidence to generate mid-PoV.
  • Always-On covers Windows, macOS, Android and iOS — not Linux, and the bypass features are client-gated (user bypass with reason: the Windows and macOS Clients and iOS 5.6+; Windows 5.9+ also sets how long a bypass lasts). Scope the parity criterion to the platforms it applies to.
  • If IT tools relied on DirectAccess manage-out — reaching into remote machines for patching or support — capture that as a scoped item in the test-case register rather than assuming parity. It is a different workflow, and it deserves its own criterion or its own follow-on, not a silent assumption.
  • Experience Monitoring has edges — application metrics are calculated for outbound TCP traffic, and some data can be delayed up to 30 minutes. Do not promise a baseline from minute one of a swap.

Unwinding cleanly: if the decision is a no, the exit is the rollback drill at cohort scale — remove the Cato Client per device, re-apply the DA client GPO, reboot — and because the NLS, PKI and IP-HTTPS gateway ran untouched throughout, the estate is exactly where it started; then disable the pilot policies and de-scope the SCIM group if it was created for the PoV. If the decision is a yes, do none of it: the pilot policy set is wave one of the six-step migration path above, and the cohort never swaps back.
