Ransomware & Advanced Threat Prevention

Ransomware is not one event — it is a chain: initial access, payload delivery, command and control, lateral movement, exfiltration, encryption. Every link in that chain has to cross the network, and on Cato every flow — WAN, internet, cloud and remote user — crosses the SPACE engine. This use case shows how Cato breaks the chain at every network-visible stage, and how XDR turns the surviving weak signals into one correlated story.

Business objective

Why this matters

Ransomware remains the board-level cyber risk: it stops production lines, closes tills and takes patient systems offline — and the extortion now runs twice, once for the decryption keys and once for the stolen data. Yet the attack itself is rarely exotic. It is a sequence of ordinary-looking network events: a phishing link clicked, a file downloaded, a beacon out to a server nobody has heard of, SMB sessions fanning out to the file servers and backups.

The objective: make every stage of that chain cross an inspection point, so a single missed control never becomes an encrypted estate — and see the whole attack as one story, not fifty unrelated alerts.

The attack, stage by stage

Every link in the chain touches the network

Defenders only need to break one link; the attacker needs all six. The table below is a useful whiteboard in discovery — for each stage, ask which control in the current estate would actually see it.

StageWhat the attacker doesWhat it needs from the network
DeliveryPhishing link, malvertising, drive-by download, trojanised installerAn outbound web or DNS request to attacker infrastructure
ExploitExploits an unpatched CVE on an exposed service or applicationA connection — inbound or outbound — carrying the exploit
PayloadDownloads and executes the ransomware binary or loaderA file transfer that has to cross the wire
C2Beacons to command and control for keys and instructionsOutbound sessions to attacker-controlled domains and IPs
Lateral movementSpreads to servers, backups, OT and other sitesEast-west traffic across the LAN and WAN
ExfiltrationStages and steals data for double extortionBulk outbound transfer to attacker storage

The chain only needs one gap

Appliance-based inspection covers the traffic that happens to pass the appliance. Remote users split-tunnel around it, branch internet breakout skips it, and OT/IoT devices cannot run the EDR agent that is supposed to compensate. One uninspected path is all the chain requires.

Signals nobody joins up

Each stage looks minor on its own: one odd DNS lookup, one blocked download, one IPS hit. The tools that saw them don't talk to each other, and the SIEM project that was meant to correlate them is measured in quarters, not minutes.

Discovery question

“If ransomware detonated on a laptop in one of your branches tonight, what stops it reaching your backup servers — and would anyone see the C2 traffic before the encryption starts?”

The Cato solution

Break the chain at every stage

On Cato there is no unexamined path. Every flow from every site, remote user and cloud instance traverses a Cato PoP, where the Single Pass Cloud Engine (SPACE) inspects it once against every engine — SWG, DNS security, IPS, next-generation anti-malware (NGAM), cloud sandboxing, firewall and DLP — with TLS inspection at cloud scale and no appliance capacity to ration. The same chain that needs six steps to succeed meets six independent controls:

Legitimate traffic — unaffected Ransomware kill chain — blocked at every stage
Six stages, six independent controls — and XDR correlates every blocked attempt into a single incident story.

From fifty alerts to one story

Even a partially successful attack leaves weak signals: a DNS lookup here, a blocked download there, an unusual SMB fan-out at 02:00. Cato XDR correlates them automatically — the events already share one data lake, one identity model and one timeline — and presents a single story mapped to MITRE ATT&CK tactics and techniques. No collector deployment, no SIEM integration project. And for organisations without a 24×7 SOC, the optional Cato MDR service has Cato analysts triaging and responding to those stories around the clock.

Demo runbook

How to run the demo

Safe to run live

The malware step uses EICAR — the industry-standard harmless test file. Nothing malicious touches the tenant, but the block behaviour and events are exactly what a real payload would trigger.

  1. Open on the threat landscape

    Monitor → Threats Dashboard

    Show the tenant-wide picture: threat types, top attacked hosts, trends across sites and remote users. Frame it — every event on this screen was caught because the traffic had to pass a PoP. There is no “behind the firewall” here.

  2. Block a live “malware” download

    Security → Anti-Malware

    Show the NGAM and sandboxing policy, then — as a user (say, Priya on a remote client) — download the EICAR test file in a browser. The download is blocked inline; show the block page and the resulting anti-malware event. Note that novel variants follow the same path into the cloud sandbox.

  3. Show an exploit attempt stopped by IPS

    Monitor → Events

    Filter to IPS events and open one from a vulnerability scanner or CVE exploit attempt — internet-facing services collect these constantly. Point out the CVE reference in the event and explain virtual patching: the protection was live in every PoP long before anyone scheduled a patch window.

  4. Open the XDR story

    In the XDR Stories Workbench, open a story that correlates related signals — the anti-malware block, IPS hits, suspicious DNS — into one incident with a timeline, affected users and devices, and MITRE ATT&CK mapping. This is the “fifty alerts become one story” moment; let it land.

  5. Show the containment layer

    Security → WAN Firewall

    Walk a segmentation rule that would stop the spread — for example, the HQ lab site's user subnets denied to the London DC backup VLAN except named services. East-west traffic between sites and VLANs is firewalled in the PoP; hit counts prove it is enforced, not aspirational.

  6. Close on operations: who watches at 03:00?

    Everything shown is prevention and detection on one platform. For customers without a 24×7 SOC, close on the Cato MDR service — Cato analysts monitoring the same XDR stories, triaging and responding around the clock, on the platform they already run.

PoV runbook

How to prove it in the customer's tenant

The demo tells the kill-chain story on our tenant; this PoV runs a kill-chain-controls pilot on theirs — each network-visible stage from the table above becomes a demonstrated control, evidenced by a safe, staged, change-controlled test. Nothing in this runbook involves real malware or contact with real attacker infrastructure: delivery uses the KB's harmless EICAR-style test file, exfiltration uses a fictional-data document you create, and the C2 stage is evidenced from monitor logs rather than simulated. Agree the criteria below before configuring anything, per Running a Cato PoV — every drill has a date in the test-case register and a named owner on the customer side.

Prerequisites — agree before week one
  • Scope: one pilot branch socket plus a client cohort (5–20 users), and one WAN destination site — a DC or second branch — for the east-west test. The LAN Firewall stage needs the pilot site on a Socket: the policy is enforced locally on the Socket, not at the PoP.
  • Safety and change control: every artefact is safe by construction — the KB's documented EICAR-style test files and a fictional-data document for the DLP stage. Each drill has a booked date in the register and sign-off from the customer's security team. Never real malware; never a connection to real C2 infrastructure.
  • Licences: IPS and Anti-Malware active (NG Anti-Malware where scoped — it requires the base service); Suspicious Activity Monitoring is included in the IPS licence. Data Control rules need the CASB and DLP licences. XDR stories need the XOps licence — the licence-honesty note in the SOC/XDR PoV applies verbatim.
  • TLS inspection staged first: the HTTPS variant of the delivery drill depends on it, and the KB is explicit that DLP content inspection requires it. Follow TLS Inspection: Staged Rollout Playbook and clear the scope with whoever owns privacy.

Configuration walkthrough — one stage, one control, monitor-first

  1. Pin the scope, book the drills, take the baseline

    Network → Sites Monitor → Topology

    Confirm the pilot socket and cohort are live, then put a date against every kill-chain drill in the test-case register — the drills only carry weight because they are staged and announced, not sprung. Dated topology and policy screenshots are evidence item zero.

  2. Delivery — block the safe test file on both paths

    Security → Anti-Malware

    Enable Anti-Malware (and NG Anti-Malware where licensed) and run the KB's EICAR test from a machine behind the socket, then as a cohort user on the Client. The HTTP variant is blocked without inspection; the HTTPS variant downloads cleanly until TLS inspection is staged — a useful before/after exhibit, then a block. The full two-path discipline, including timing the policy propagation, is already written up in Consistent Security Everywhere — PoV runbook; run this stage to that recipe and file the artefacts against this criterion.

  3. C2 — monitor the real thing, simulate nothing

    Security → IPS

    Set IPS to Monitor for the scoped directions (semantics in the consistent-security PoV), and enable Suspicious Activity Monitoring on the Suspicious Activity tab — monitor-only by design, because the traffic is suspicious rather than definitely malicious. The KB documents no safe C2 simulation, so this criterion is evidenced from monitor logs: over the pilot window, filter Events to the IPS and Suspicious Activity sub-types and let the tenant's own traffic — scanner noise, risky destinations, odd HTTP patterns — make the case. If the customer wants to see inline IPS enforcement fire on demand, the KB's documented safe drill is a Geo Restriction rule tested against a site hosted in the blocked country: run it from the site path only, and allow up to ten minutes for the rule to take effect.

  4. Lateral movement across the WAN — monitor, then one agreed block

    Security → WAN Firewall

    The WAN Firewall rulebase is ordered and ends in an implicit any-any block — east-west is deny-by-default, the opposite of the Internet Firewall. Add a rule covering pilot-site user subnets towards the DC or backup destinations with Track = Event and let a week of events map who actually talks east-west. Then, in the booked change window, make the one agreed change of the pilot: block the agreed flow (say, SMB from a pilot workstation towards the backup VLAN) and run the test. The blocked event — user, source, destination, rule — is the artefact.

  5. Lateral movement inside the site — LAN Firewall on the Socket

    Security → LAN Firewall

    The LAN Firewall is a single account-wide policy, scoped per site and enforced locally on the Socket — the traffic is routed by the Socket and never sent to the PoP. A LAN Network rule defines the transport; the LAN Firewall rules nested beneath it allow or block within that scope — mirror the WAN stage: track events first (they land under the LAN Firewall event sub-type), block only what was agreed. App/category conditions need Layer 7 rules enabled on the pilot site, and same-site traffic that matches no LAN rule is treated as WAN traffic — so the two stages together close the east-west picture.

  6. Exfiltration — a DLP monitor rule and a staged fictional upload

    Security → App & Data Inline Security → Data Types & Profiles

    Build a Data Control rule scoped to the pilot cohort: upload activity, a DLP profile built from predefined data types (UK PII or credit-card types read well), action Monitor. Stage the drill: a document seeded entirely with fictional data — invented names, standard test card numbers — uploaded to a personal cloud-storage app by a cohort user, on the booked date. The resulting Apps Security event names the DLP profile, file name and user: the double-extortion stage, caught on the wire, with nothing real at risk.

  7. Convergence — one dashboard, and stories where licensed

    Monitor → Threats Dashboard

    Close the loop where the customer will live day-to-day: the Threats Dashboard aggregates IPS, DNS Protection and Anti-Malware activity (up to 90 days) and its View Events drill-down lands on the exact rows behind each widget — capture it with the delivery and C2 evidence in view. Where the account holds the XOps licence, run the stories criterion to the SOC/XDR PoV runbook — including its gotcha that the EICAR drill proves the sensor, not the story: let stories stand on real traffic, and keep this criterion licence-honest.

What good output looks like

The wrap-up reads as five stages, five artefacts: two Anti-Malware blocks with different sources, a window of IPS and Suspicious Activity events from real traffic, one blocked east-west flow, one monitor-mode DLP catch, and the dashboard (or story) that shows them together. Every one is dated against a booked drill in the register — staged evidence, not lucky timing.

Troubleshooting

🔐

HTTPS test file downloads fine

The flow wasn't inspected. Check the TLS Inspection policy order for a bypass rule catching the test source, confirm the root certificate on the test device, and remember inspection is auto-bypassed for some operating systems — the checklist is in the consistent-security PoV.

🖥️

The endpoint AV eats the test file first

Desktop AV quarantining EICAR before the browser saves it muddies "was it blocked on the wire?". The network artefact is the Cato block page and the Anti-Malware event — read those, not the disk — or agree a temporary endpoint-AV exclusion for the test directory with the endpoint team.

📡

No C2-stage events

The IPS policy must be enabled before SAM can be switched on, a new IPS rule can take up to ten minutes to become effective, and a quiet ten-user cohort gives the sensors little to say. Check IPS state, widen the Events window, and let the pilot run — this criterion accrues, it doesn't fire on demand.

🧱

The lateral test wasn't blocked

First match wins — an earlier, broader allow is swallowing the flow. Also check which policy actually saw it: same-site traffic that matches no LAN Firewall rule is treated as WAN traffic, so the event may be sitting under the WAN Firewall rather than the LAN Firewall sub-type.

📄

The DLP rule never fires

No TLS inspection means no content inspection — it is a hard prerequisite. Then check the rule's activity direction covers upload, the profile's data-type thresholds against your fictional document, and that the account holds both the CASB and DLP licences.

📊

LAN Firewall evidence looks missing

LAN Firewall traffic does not appear in the app and network analytics dashboards — that is documented behaviour, not a fault. Filter Events by the LAN Firewall sub-type for the artefact, and set expectations before the customer goes looking.

Gotchas & clean exit

Honest caveats
  • This pilot evidences network-layer controls — and only those. Endpoint detection and response, backup integrity and recovery testing are separate domains with their own owners; a ransomware programme needs all of them, and this PoV should say so in the wrap-up rather than imply coverage it didn't test.
  • Safe by construction, or not at all: EICAR-style files and fictional data are the only test artefacts. If a stage cannot be evidenced safely (C2), it is evidenced from monitor logs — never by simulating the attacker.
  • One block flip: everything runs in monitor except the single agreed lateral-movement block, in its change window. Resist requests to "just block it all" mid-pilot — that is a production rollout decision, and it belongs after the decision meeting.
  • Licence edges: stories need XOps (see the SOC/XDR PoV), Data Control needs CASB plus DLP, and NG Anti-Malware needs the base service — write entitlements against each criterion before week one.

Exit: remove the WAN and LAN drill rules and the DLP monitor rule, return IPS and Anti-Malware to the agreed end-state, and publish once — remembering a published revision cannot be un-published, so the before-state you recorded at baseline is the map for unwinding. Export the dated artefacts before tenant access ends; the Administration → Audit Trail record of everything the pilot added and removed doubles as the closing exhibit: one console, five stages, one story.
