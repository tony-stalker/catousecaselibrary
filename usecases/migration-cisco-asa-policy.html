Cisco ASA Policy Migration

An ASA-only estate carries a decade of interface ACLs, nested object-groups and NAT statements — and almost nothing above layer 4. That makes this policy project unusual: the translation workload is smaller than a full NGFW estate, and the greenfield workload is bigger. This page works through the ASA policy stack construct by construct — ACLs rationalised on hitcnt evidence and split into Cato's WAN and Internet firewall bases, the three-section NAT table dissolved deliberately rather than copied, AnyConnect posture restated as Device Posture — and is honest about the rest: SWG, CASB, DLP and TLS inspection have no ASA ancestor, so they are built greenfield from Cato best-practice baselines. That is the uplift the customer is buying, not a gap.

Business objective

Why the ASA rulebase deserves better than a copy

Swapping the appliance for a Socket is a routing exercise — the companion playbook, Cisco ASA to Cato, covers the estate, the EOL calendar and the cutover waves. The policy side is where the project earns its keep: a perimeter ASA typically carries years of accumulated ACEs, many of them dead, nested object-groups hiding duplicate and unreferenced entries, and a NAT table whose real dependencies are invisible in the ACL export. Copying all of it across “to be safe” imports the technical debt into a brand-new platform and makes the Cato rulebase unauditable on day one.

The Cato Professional Services approach is a four-phase pipeline, applied per policy domain: EXPORT the configuration and its usage evidence → REVIEW & MAP — rationalise on per-ACE hit counts, discard dead weight with sign-off, then map surviving intent to Cato constructs → DEPLOY monitor-first, so every translated rule earns event evidence before it can hurt anyone → OPTIMISE — tighten to block on that evidence. Review-and-map, not lift-and-shift: per-interface rule bases collapse into one global policy, and the clean-up is what makes the mapping tractable.

Scope note: this page assumes the ASA-only estate — no Umbrella, no Cisco SD-WAN. If the account also runs Umbrella or Catalyst/Meraki SD-WAN, the policy translation is a different, larger exercise: use Cisco Policy Migration, which maps the Umbrella web, app-control and DLP estates alongside the ASA/FTD firewall.

Discovery question

“How many of your ACEs show hitcnt=0 today — and when were the counters last reset? And separately: what inspects an upload from a corporate laptop to a personal cloud drive right now?” The first answer sizes the clean-up; the second is almost always “nothing”, and it frames the greenfield half of this page.

Domain 1 — FW rules

Interface ACLs, object-groups & hit-count rationalisation

The construct. ASA policy is L3/L4: ordered ACLs applied per interface (inbound, with an implicit deny at the end), built from ACEs that reference nested network, service and protocol object-groups, with interface security levels and same-security-traffic doing the zone work. Managed through CLI and ASDM, occasionally CDO. There is no separate web or application policy to export — everything the firewall decides, it decides here.

Export. Everything needed lives in a handful of CLI artefacts — capture them per device, at the start and end of a representative counting window: 

# The full configuration — objects, ACLs, NAT, crypto, tunnel-groups
show running-config
# (more system:running-config additionally reveals masked secrets — capture under change control)

# The single most valuable artefact: object-groups pre-expanded into ACEs, with live hit counts
show access-list
show access-list | include hitcnt=0   # the cull candidates

# Object inventory for the mapping workbook
show object-group
show names

# The golden-flow harness: simulate a flow through route lookup, ACL, NAT and VPN phases
packet-tracer input inside tcp 10.20.4.20 12345 10.20.8.15 1433

The hit-count discipline. show access-list reports a live hitcnt= per expanded ACE — the usage evidence the whole rationalisation stage runs on. Two caveats must survive into the project plan. First, counters reset on reload and on clear access-list counters, so a single snapshot proves nothing: establish a counting window (30–90 days, spanning a month-end or quarter-end) and diff the start and end captures. Second, zero-hit is not dead — DR paths, annual jobs and break-glass rules legitimately show hitcnt=0. Culls need change-control sign-off, not automation; park contested ACEs as a disabled, documented rule group in CMA rather than silently dropping them. Where an FTD or an SFR module is in the picture, FMC (6.4+) and CDO report the equivalent access-policy hit counters.

ASA constructCato constructNotes

Interface ACL — internal → internet ACEs Internet Firewall rules (blocklist, implicit allow) The opposite posture — an egress permit usually needs no rule at all; see the direction-inversion gotcha

Threat-detection / shun / uRPF settings Cato IPS and platform protections No translation — note the intent, verify coverage in monitor mode

Semantic gotchas. Direction inversion is the headline trap: an interface ACL ends in an implicit deny, but Cato splits postures — WAN Firewall allowlist, Internet Firewall blocklist — so a raw copy puts outbound exceptions into the wrong base and inverts their meaning. Shadowing on merge is the one that surfaces late: both models are first-match, but consolidating several per-interface ACLs into one ordered base can make rules collide that never met on the ASA — re-order deliberately and re-test after every re-order. The regression harness for both is a golden flow list: the 20–50 flows the business actually depends on, each with its expected verdict — proven with packet-tracer on the ASA side at EXPORT, and against CMA events on the Cato side at DEPLOY.

Strategy. Export with hit counts over the counting window → cull zero-hit ACEs with sign-off, park the contested ones → flatten the object model and push it via the API or Terraform → split survivors by direction into the two bases → deploy allow-and-track / monitor first → tighten to block from event evidence.

Domain 2 — NAT

The NAT table: dissolve it deliberately

The construct. ASA NAT is a three-section table evaluated in order — Section 1 manual/twice NAT, Section 2 object NAT, Section 3 after-auto — carrying four very different intents: dynamic PAT for egress, static NAT publishing a handful of services, identity/no-NAT exempting VPN traffic, and the occasional destination-conditional twice NAT, hairpin or DNS-doctoring rule papering over an addressing quirk. None of it “translates”: each class is either dissolved by the platform, re-homed on its own change window, or redesigned. Export the real table, not the config's intent: 

# The NAT table in evaluation order, with per-rule detail
show nat detail

# Live translation volume — a sanity check on what is actually in use
show xlate count
ASA NAT classCato outcomeNotes
Object NAT — dynamic PAT for egress Nothing — PoP egress NAT is inherent Delete, don't map. Record the old egress IPs: every SaaS tenant restriction and partner allowlist keyed to them needs updating at cutover
Static NAT / port-forward publishes Remote Port Forwarding on Cato allocated IPs, or Local Port Forwarding Better: anything only ever accessed by users moves behind ZTNA or clientless access instead of staying internet-exposed. Each publish carries DNS, partner and certificate dependencies — inventory it separately from the ACL work
Identity NAT / no-NAT for VPN traffic Not needed — Cato WAN traffic is routed, not NATed Its presence marks which flows were VPN-bound: useful discovery data, zero migration output
Twice NAT with destination logic · hairpin NAT · DNS doctoring No equivalent — redesign, not translation Split-horizon DNS replaces hairpins; destination-conditional NAT usually indicates an overlapping-subnet or partner quirk that needs an explicit design decision at MAP

The gotcha that breaks cutovers. Embedded NAT dependencies are invisible in the ACL export: a partner VPN pointed at a NATed address, hairpin access to a published service from inside, a SaaS allowlist keyed to the PAT address. Every one breaks at cutover if it was not inventoried from show nat detail in discovery — which is why NAT is its own domain on this page, not a footnote to the ACLs.

Domain 3 — Remote access & posture

AnyConnect artefacts: summarise here, execute elsewhere

The remote-access play — AnyConnect end-of-life dates, the Secure Client 5.x forced transition, cohort waves, helpdesk playbook — is owned end-to-end by AnyConnect to Cato Client; do not re-plan it here. What belongs in the policy workbook are the artefacts on the ASA itself, because two of them have no export path at all:

ASA artefactCato constructNotes
Tunnel-groups, group-policies, split-tunnel ACLs Client Connectivity Policy + app access rules Config exports in show running-config, but the model changes — full walkthrough on the AnyConnect page
DAP rules / HostScan (Secure Firewall Posture) checks Device Posture profiles + posture-gated connectivity No export path — recreate from written intent. Cato posture is continuously evaluated, not connect-time only; budget real workshop time, this was manual even ASA→FTD
Local users, AAA, LDAP attribute maps IdP SSO (Entra ID / Okta) + SCIM group membership Attribute-map logic becomes group design in the IdP — sequence identity before any user-scoped rule
WebVPN / clientless portal Cato clientless browser access Retires the internet-listening VPN web endpoints — the surface class exploited in the 2025 ASA zero-days (CVE-2025-20362)
Check the certificate estate now

AnyConnect machine certificates, internal CA chains and identity certs (show crypto ca certificates) do not migrate by themselves — and an expiring certificate mid-migration looks exactly like a Cato failure. Capture expiry dates in discovery and plan renewals around the waves.

Domain 4 — SWG · CASB · DLP · greenfield

Nothing to export — and say so in the room

Be honest about this, because it changes the project plan. An ASA-only estate typically has no SWG or URL filtering, no CASB, no DLP and no TLS inspection — and where NGFW features exist they came from the ASA FirePOWER (SFR) service module, which dies with the hardware and whose configuration even Cisco's own Secure Firewall migration tool does not convert. There is no artefact to go hunting for: these domains are greenfield builds from Cato best-practice baselines, not translations — and that is most of the policy project by effort. Framed properly, it is the upgrade the customer is buying, not a migration gap.

In the ASA estateCato constructWhat changes
Nothing — no URL/web filtering SWG categories in Internet Firewall rules Category enforcement for every site and remote user, from a best-practice baseline in monitor mode
Syslog/NetFlow reporting only App Analytics + Cloud Apps Dashboard Continuous shadow-IT discovery with risk scores — visibility the estate has never had
Nothing — no CASB CASB application rules with activity controls and tenant restrictions Allow the app, govern the activity — upload, download, share — instead of a port-level yes/no
Nothing — no network DLP DLP profiles with predefined data types (PCI, PII, credentials, source code) The input is a data-protection workshop, not a config file — start from predefined types
Nothing — no TLS inspection Cato TLS Inspection policy The fidelity prerequisite for the other three — staged by category and pilot group, with no appliance headroom maths
SFR module IPS/AMP/URL (where licensed) Cato IPS + Next-Gen Anti-Malware Module config is not convertible even to FTD — rebuild from Cato baselines in monitor mode

Build sequence (best practice). Switch the greenfield engines on from day one of co-existence, in monitor/report mode — every week the project runs then generates the event evidence the OPTIMISE phase tightens against. Stage TLS inspection first, by category and pilot group, because CASB activity control and DLP content inspection cannot see what is not decrypted. Run shadow-IT discovery over a representative business cycle; classify the SaaS estate sanctioned / tolerated / unsanctioned; write CASB and DLP rules in monitor mode; enforce highest-confidence rules first. Day-one blocking is how greenfield security projects die — monitor-mode evidence is how they succeed.

Position it as the uplift it is

“Nothing on the ASA inspects an upload, classifies a SaaS app or reads a TLS payload — so there is nothing to migrate in these domains, and nothing to get wrong. Day one on Cato you will see every app in use, scored for risk, and we turn that into control at your pace: monitor first, then enforce.”

Worked example

Before → after: an ACL and a NAT table translated

Illustrative only

The extract and tables below are composed to show the translation pattern — documentation- and private-range example addresses and invented hit counts, not console exports; a real rulebase runs to hundreds of lines — though the screenshot after the CMA table is the real console from a live demo tenant. Every surviving row still travels the full pipeline: rationalise on usage, map, deploy monitor-first, enforce on evidence.

Before — ASA extract (illustrative)

# show access-list INSIDE-IN — extract (hitcnt over a 60-day window)
access-list INSIDE-IN line 8  extended permit tcp object-group BRANCH-NETS object-group DC-APPS eq https (hitcnt=61204)
access-list INSIDE-IN line 9  extended permit tcp object-group BRANCH-NETS host 10.20.8.15 eq 1433 (hitcnt=8830)
access-list INSIDE-IN line 12 extended permit ip host 192.0.2.44 any (hitcnt=0)
access-list INSIDE-IN line 15 extended permit tcp any any eq 8443 (hitcnt=3)

# show running-config nat — the PAT and one publish
object network INSIDE-NET
 subnet 10.20.0.0 255.255.0.0
 nat (inside,outside) dynamic interface
object network WEB-PORTAL
 host 10.20.8.30
 nat (dmz,outside) static 203.0.113.40 service tcp 443 443

After — Cato CMA (illustrative)

#NameSourceDestination / AppServiceActionTrack
WAN Firewall — allowlist posture
1 Branches → DC application servers Sites: all branch sites Host group: DC-Apps HTTPS (TCP/443) Allow Event
2 Branches → finance SQL Sites: all branch sites Host: 10.20.8.15 TCP/1433 Allow Event
3 Parked — line 12 pending sign-off Host: 192.0.2.44 Any Any Disabled —
Line 15 (any-any on TCP/8443, three hits) is not recreated: as egress it needs no permit under the Internet Firewall's default allow, and its intent — if anyone still defends it — returns as a scoped rule, not an any-any.

The NAT table produces no rules at all. The INSIDE-NET dynamic PAT dissolves — egress NAT is a property of the PoP — with the old egress IP recorded for the allowlist-update checklist. The WEB-PORTAL publish is re-homed as Remote Port Forwarding on a Cato allocated IP in its own change window (DNS TTLs lowered first, rollback = DNS revert) — or, if only employees ever used it, it moves behind ZTNA/clientless access and stops being internet-exposed at all.

What changed in translation

  • Direction chose the base. The east-west ACEs became WAN Firewall allowlist rules — the posture that matches the ASA's implicit deny. The egress ACE was not copied into the Internet Firewall, where a permit means nothing under default allow.
  • Hit counts decided survival. Two ACEs translated, one parked as a disabled rule pending change-control sign-off, one retired — the discard pile is an output of the migration as much as the rules that survive.
  • Object-groups flattened. BRANCH-NETS and DC-APPS became global hosts, ranges and groups — expanded first by show access-list so dead entries were visible before translation.
  • The NAT table dissolved. PAT became a platform property; the one real publish moved on its own change window; nothing NAT-shaped was “translated”.
Cross-domain practices

Rules that hold across the whole exercise

🧭

Respect the default postures

Cato's WAN Firewall is an allowlist (implicit block); the Internet Firewall is a blocklist (implicit allow). Every ACE is sorted by direction before it is mapped — a raw copy inverts the meaning of outbound exceptions, and egress posture is a decision, not a translation.

⏱

Count before you cull

Hit counters reset on reload and on clear access-list counters — a single snapshot proves nothing. Diff captures across a 30–90 day window that includes a month-end, and remember zero-hit is not dead: DR and break-glass rules earn a parked group, not silent deletion.

🟠

Monitor, then block

Every translated rule and every greenfield engine — IPS, anti-malware, SWG categories, CASB, DLP — starts in monitor. Enforcement is earned per rule with event evidence: the pipeline's amber-to-green transition, never a big-bang flip.

🪪

Sequence identity first

LDAP attribute maps and AAA logic become IdP group membership — provision SSO and SCIM sync before mapping any user-scoped rule, and design the groups that DAP logic will be restated against. Name drift here breaks rules silently.

🧱

Objects before rules

Flatten the nested object-groups, delete the unreferenced and duplicate entries, and push the clean object model through the GraphQL API or Terraform provider first — then build rules on top of it. Importing object sprawl recreates the debt you just paid down.

📊

Validate with the golden flows

The regression harness is the agreed golden flow list: packet-tracer proves the ASA-side verdicts at EXPORT, CMA events prove the Cato-side verdicts at DEPLOY, and monitor-mode hits are compared against the hitcnt deltas for the same window before any wave cuts over.

The policy pipeline

EXPORT → REVIEW & MAP → DEPLOY → OPTIMISE

One pipeline, two kinds of input. The ACLs, the NAT table and the remote-access artefacts enter through EXPORT and are rationalised before anything is mapped — dead ACEs and dissolved NAT leave at review and are never translated. The greenfield domains have nothing to export: they enter at DEPLOY as Cato best-practice baselines, skipping translation but not the monitor-first discipline. Everything that reaches DEPLOY earns its promotion to enforcement from events and hit counts.

Monitor first — log, don't block Enforce — promoted on evidence Discarded — culled at review with sign-off Telemetry — validates every stage
The ACLs, NAT table and posture artefacts are exported once and rationalised against the hit-count window — zero-hit ACEs and dead objects exit at review, with sign-off, and are never translated. The greenfield domains skip EXPORT entirely: SWG, CASB, DLP and TLS inspection enter at DEPLOY as Cato best-practice baselines in monitor mode. Both streams are promoted to enforcement only when events and hit counts prove the behaviour is intended.
Demo runbook

Running the policy workshop

Format

This runs best as a working session, not a show-and-tell: ask the customer to bring show access-list and show nat detail output and translate a few real lines live. Nothing sells the model like watching their own policy land in it — and the answer to “what do you run for SWG, CASB and DLP today?” is almost always “nothing”, which sets up the greenfield story before you open the console.

  1. Frame the pipeline and agree the counting window

    Walk the EXPORT → REVIEW & MAP → DEPLOY → OPTIMISE diagram. Agree scope and owners: which ASAs, who signs off a cull, when the counters were last reset, and the 30–90 day window the hitcnt evidence will be read over.

  2. Show the two firewall postures

    Security → WAN Firewall Security → Internet Firewall

    One global rulebase, no interfaces, no security levels. Point out the opposite defaults — WAN allowlist, Internet blocklist — then translate one of their east-west ACEs live and discuss where their egress posture should land.

  3. Walk the object model and the automation path

    Administration → API & Integrations

    Show hosts, groups and custom services, then the API keys page — the expanded ACL output is structured text, so object translation is scriptable end-to-end via the GraphQL API or the Terraform provider rather than re-keyed by hand.

  4. Have the NAT conversation early

    Walk the four NAT classes against their show nat detail: the PAT that dissolves, the publishes that move on their own change windows (or behind clientless access), and the twice-NAT quirks that need a design decision — plus the checklist of allowlists keyed to the old egress IPs.

  5. Show posture recreated from intent

    Access → Device Posture Access → Client Connectivity Policy

    Build a Device Posture profile live — AV/EDR presence, disk encryption — and gate a connectivity rule on it. Be explicit that DAP/HostScan logic has no export path: this is restated intent, evaluated continuously rather than at connect time.

  6. Show the greenfield destination state

    Monitor → Cloud Apps Dashboard Security → DLP Configuration

    Shadow-IT discovery running with zero configuration, a CASB tenant-control rule, and a DLP rule combining a predefined data type with a file-type condition — the domains the ASA never had, on from day one in monitor mode.

  7. Stage the fidelity prerequisite

    Security → TLS Inspection

    Walk the staged TLS inspection policy — bypasses first, then phased inspect rules by category and pilot group — and note that CASB activity control and DLP content inspection hang off this switch, with no appliance throughput deciding the scope.

  8. Close on the evidence loop

    Monitor → Events

    Filter events to a single monitor-mode rule and show the hit evidence that would justify flipping it to block — the OPTIMISE phase they will live in for the first months, and the audit trail for every promotion and every cull.
