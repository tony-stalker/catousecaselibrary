Automation at Scale with API, catocli & Terraform

Operating tens or hundreds of sites by clicking through a console is not a strategy. Everything in the Cato Management Application is driven by the Cato GraphQL API — so sites, policy and monitoring can be code: version-controlled, peer-reviewed, deployed by a pipeline and rolled back like any other change.

Business objective

Why this matters

Networks grow faster than network teams. An acquisition adds twenty sites overnight; a retail rollout adds a hundred over a quarter. If every site, every firewall rule and every report is a sequence of clicks, scale means either more head-count or more mistakes — usually both.

The objective: make the network operable as code. New sites deploy from a template with zero console time, policy changes go through review and can be rolled back, and the security estate feeds the tooling the organisation already runs — SIEM, CI/CD, ITSM. Because the CMA itself is built on the same GraphQL API that customers use, there is no "automation subset": anything you can click, you can code.

The problem

Click-ops does not scale

Operating by hand

  • Every new site is a manual, snowflake configuration
  • Bulk policy changes mean hours of repetitive clicking
  • No review step — a typo goes straight to production
  • No rollback beyond "remember what it looked like"
  • Reporting is a person exporting screenshots monthly

Operating as code

  • Sites are templated resources — apply once, repeat forever
  • Policy lives in Git: diff, peer review, merge, deploy
  • Rollback is git revert plus a pipeline run
  • Events stream continuously into the SIEM
  • Reports generate and deliver themselves on a schedule
Discovery question

“Walk me through your last multi-site change — how long did it take, how many people touched a console, and if it had gone wrong, how would you have rolled it back?”

The Cato solution

One API, three ways to consume it

The Cato GraphQL API at api.catonetworks.com is the programmatic surface of the entire platform — sites, sockets, policy, entities, events and analytics. Around it sit two official tools, so teams can automate at whatever altitude suits them:

GraphQL API

Query and mutate anything in the account — the same API the CMA runs on. Ideal for SIEM feeds, custom integrations and scripted changes from any language.

catocli

The Python CLI that wraps the API — every query and mutation as a shell command. Perfect for ad-hoc lookups, quick bulk jobs and glue scripts in a pipeline.

Terraform provider

The official catonetworks/cato provider: declare sites, interfaces and policy as resources. Plan shows the diff; apply converges the account to the code.

A realistic first hour with the toolchain looks like this:

# pip install catocli
catocli query entityLookup -accountID <your-account-id> '{"type":"site"}'
terraform plan   # cato_socket_site resources for 12 branch sites
terraform apply  # sites appear in CMA in minutes
API-driven change / data flow
Site and policy definitions merge in Git; a CI runner drives the GraphQL API to create sites and apply policy, while the events feed streams continuously into the SIEM.

What teams automate first

🚀

Zero-touch site rollout

Template a branch once, then apply it per site — the M&A play: an acquired estate becomes a Terraform module and lands on the WAN in days, not quarters.

🔁

Bulk policy with review & rollback

Firewall rules live in version control. A change is a pull request: diffed, reviewed, applied by pipeline — and reverted the same way if needed.

📡

Events into the SIEM

The events feed streams security and connectivity events into Splunk, Sentinel or any collector — Cato telemetry alongside everything else the SOC watches.

🗓️

Scheduled reporting

Pull analytics and entity data on a schedule and publish to whoever needs it — no more monthly screenshot-and-paste exercises.

Demo runbook

How to run the demo

Before you demo

Ask what they automate today — Terraform elsewhere? A SIEM in place? Anchor on their toolchain: the message is that Cato joins it, not that they must adopt a new one.

  1. Start at the API surface

    Administration → API & Integrations

    Show where API keys are created and scoped. Make the architectural point: the CMA is a client of this same GraphQL API — there is nothing the console can do that code cannot.

  2. First query with catocli

    Install the CLI (pip install catocli) and run an entityLookup for sites against the demo account. Seconds from install to a live inventory of the estate — no SDK, no boilerplate.

  3. Create a site with Terraform

    Run terraform plan on a cato_socket_site definition and walk the diff, then terraform apply. Emphasise the plan step: the change is reviewed before anything touches production.

  4. Watch it appear in the CMA

    Monitor → Topology

    The new site is on the topology map within minutes, alongside London DC, Glasgow and the rest of the estate. Code on one screen, the live WAN on the other.

  5. Make a tagged policy change via API

    Push a firewall rule change through the API with a change tag (ticket reference or commit hash). This is the bulk-change story: one script, every site, one audit entry per mutation.

  6. Prove attribution in the Audit Trail

    Administration → Audit Trail

    Show the API change attributed to its API key, with the before/after values. Automated changes are as accountable as console changes — often more so.

  7. Close on the SIEM feed

    Mention the eventsFeed API: the same platform that just deployed a site streams its security and connectivity events into their SIEM continuously — deployment, operations and detection from one API.

PoV runbook

How to prove it in the customer's tenant

This pilot is an automation-credibility exercise for a NetOps/DevOps audience: prove, in their tenant and against their toolchain, that the API surface is real, complete and accountable. The shape is deliberately conservative — read everything, change one thing, prove who changed it, tear it down cleanly, and land one event in their SIEM. Nothing in this runbook touches production traffic: it rides the management plane, inside a scope agreed in writing. Agree the success criteria below before creating any keys, per the frame in Running a Cato PoV — each has a measurement, an evidence artefact and a place where it is read out.

Prerequisites — agree before week one
  • Scope in writing: automation acts only on agreed pilot objects — a named rule prefix (e.g. pov-tf-) and, if a site is in scope, a designated test site. Terraform state contains PoV resources only, so destroy can never reach production.
  • Two API keys, least privilege each: a View key for the inventory and feed work (Viewer permissions run query calls only) and an Edit key for the Terraform change. Cato's documentation recommends setting an expiry date on Edit keys; restrict both with Allow access from IPs → Specific IP list to the runner's egress address. Creating a service key requires an admin with the Editor role.
  • Customer-side tooling: Python 3.6+ for catocli, the Terraform CLI and a Git repository — ideally their existing pipeline. Everything is outbound HTTPS to api.catonetworks.com; no inbound access is needed.
  • SIEM destination: connection details for one supported Event Integration — Amazon S3, Azure Storage, CrowdStrike, Microsoft Sentinel, Splunk or a custom HTTP push endpoint. An account can hold up to three Event Integrations, so confirm a slot is free.
  • No TLS inspection dependency: this PoV proves the management plane, not content inspection — it can run before, after or without the data-plane pilots in this library.

Configuration walkthrough

  1. Create and scope the two API keys

    Administration → API & Integrations

    Create the View key and the Edit key against the pilot account, set the expiry on the Edit key, and pin both to the runner's IP list. The key value is shown once, in the creation pop-up, and cannot be retrieved again — copy it straight into the customer's secrets vault, never into the repo. Doing this step deliberately, on screen, is itself evidence: scoped credentials are the first thing a DevOps audience looks for (Cato docs: generating API keys).

  2. Pull the full inventory with the View key

    Install and configure catocli, then pull sites and users with the read-only key. The export file is criterion one's evidence — dated and committed to the evidence repo.

    # pip3 install catocli   (Python 3.6+)
catocli configure set    # paste the View key + <your-account-id>
catocli query entityLookup -accountID <your-account-id> '{"type":"site"}' \
  -f csv --csv-filename pov-site-inventory.csv
catocli query entityLookup -accountID <your-account-id> '{"type":"vpnUser"}' \
  -f csv --csv-filename pov-user-inventory.csv

    Seconds from install to a machine-readable estate — make the point that this is the same GraphQL API the CMA itself runs on, consumed from a shell.

  3. Initialise the Terraform provider

    Switch to the Edit key (from the vault, via an environment variable — not in code) and initialise the official provider:

    terraform {
  required_providers {
    cato = { source = "catonetworks/cato" }
  }
}

provider "cato" {
  baseurl    = "https://api.catonetworks.com/api/v1/graphql2"
  account_id = "<your-account-id>"
  # token via env var — never in code or state committed to Git
}

    Known caveat, worth stating before the customer finds it: the API executes sequentially, so Cato recommends running Terraform with parallelism=1. The provider also retries with backoff by default (5 retries, 1–30 s waits), which you can tune with its retry_* arguments.

  4. Make one change as code — plan first, always

    Security → WAN Firewall

    Author one WAN firewall rule named with the agreed pov-tf- prefix, scoped to the pilot. Run terraform plan and walk the diff with the customer — this review step is the governance story. Then terraform apply -parallelism=1 and open the rulebase: the rule sits in the published revision alongside every console-authored rule, indistinguishable in effect.

  5. Prove attribution in the Audit Trail

    Administration → Audit Trail

    Filter the Audit Trail to the pilot's API key and show the change with its previous and new values. Two parameters to know from Cato's Audit Trail documentation: policy changes can take several minutes to be recorded, and the trail holds 12 months of history viewed up to 3 months at a time. Screenshot the entry — criterion three, done.

  6. Tear it down — and audit the teardown

    Run terraform destroy -parallelism=1, confirm the rule is gone from the rulebase, then return to the Audit Trail: the deletion entry, attributed to the same key. Create, change, destroy — a full lifecycle where every step is accountable. This is the moment the pilot earns the word "credibility".

  7. Land one event in their SIEM

    Administration → API & Integrations

    Two routes, pick whichever matches their estate: configure a push Event Integration (native Sentinel, Splunk or CrowdStrike connectors, S3 or Azure Storage, or a custom HTTP push), or pull events with the View key via the eventsFeed API from a scheduled job. The criterion is deliberately modest — one Cato event rendered in their SIEM console — because once one arrives, the pipeline argument is over.

Troubleshooting

🔑

401 / unauthorised on every call

The key was mistyped, has expired, or the caller's egress IP is outside the key's Specific IP list. Remember the key value is only shown once at creation — if it wasn't vaulted, revoke and re-create rather than hunting for it.

🛡️

Queries work, the mutation fails

Key scope: Viewer permissions run query API calls only — configuration mutations need the Edit key. Keep both keys and use the least-privileged one per job; that split is a feature of the pilot, not an inconvenience.

🐢

Rate-limit or concurrency errors on apply

The API executes sequentially — run Terraform with parallelism=1, per Cato's own recommendation. The provider retries with backoff (5 attempts, 1–30 s) before failing; persistent errors usually mean parallel workers, not a broken API.

🕰️

The change isn't in the Audit Trail yet

Policy changes can take several minutes to be recorded in the Audit Trail — wait before diagnosing. When searching later, note the view shows up to 3 months at a time from the 12 months held.

🔎

entityLookup returns nothing

Almost always the wrong account ID — check catocli configure show or override per call with -accountID <your-account-id>. A valid key against the wrong account returns empty results, not an error.

📤

Manual event exports keep hitting limits

The Events page exports at most 250,000 events at a time across a maximum 31-day range — fine for a one-off artefact, wrong for continuous evidence. That is what the Event Integrations and eventsFeed are for; switch route rather than scripting around the cap.

Gotchas & clean exit

Honest caveats
  • Sequential applies are slow at scale: parallelism=1 means a hundred-site apply runs one resource at a time. Say so up front — the pilot's one-rule change is instant, but size expectations for the full-estate rollout honestly.
  • Keep state small and scoped: do not import production objects into Terraform state during a pilot. State should contain only pov-tf- resources, so destroy is provably harmless — and console edits to a Terraform-managed rule will be flagged (and reverted) on the next apply, so agree that the pilot rule is owned by the pipeline alone.
  • Edit keys are production credentials: expiry set, IP-pinned, vaulted, revoked at exit. Treating them that way in front of the customer is part of the evidence.
  • Integration slots are finite: up to three Event Integrations per account — confirm a free slot before the SIEM criterion is written down.
  • Version the toolchain in the evidence doc: record the catocli and provider versions used, so the wrap-up is reproducible if the customer re-runs it after the trial.

Exit: the exit is the demo — terraform destroy already removed the pilot rule in criterion four. Beyond that: delete or revoke both API keys, remove the Event Integration (freeing the slot), and hand over the evidence repo — inventory exports, plan diffs, screenshots and the SIEM view. The Administration → Audit Trail keeps the complete, attributed record of everything the pilot created and destroyed for 12 months: the closing exhibit for an automation-credibility engagement.
