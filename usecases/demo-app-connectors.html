Demo Segment: App Connectors

Segment 6 of the 60-minute platform demo — minutes 35 to 40. Five minutes on publishing a private application without touching the network: an outbound-only App Connector beside the application, a connector group, a Private App that maps an internal address to a published domain, and a Private Access Policy rule brokered at the PoP. The user reaches the application by name; a user with no rule cannot even resolve it. Same identity, same posture, same engine as the ZTNA segment — a second way for the application to be reachable.

Why this segment

The sentence they must leave with

A private application can be published to the right users in minutes — no inbound firewall rules, no route advertisements, no readdressing, no site on-ramp — because the connector dials out, the PoP brokers the session, and nothing is reachable unless a policy rule says so.

Cato Private Access provides identity-based access to private applications without extending the network to users. Instead of the network-level connectivity a traditional VPN grants, the user gets least-privileged, application-specific access based on identity and context. Applications stay hidden and unreachable unless explicitly authorised: the user connects to the Cato Cloud, and an authorised session is brokered through an outbound-only App Connector deployed in the same environment as the application — data centre, cloud VPC or LAN. Because the connector never accepts inbound connections and needs no routing changes, Private Access can be introduced without redesigning the application network.

The previous segment showed an application behind a Cato Socket, enforced by the WAN Firewall. This one shows the four objects that replace the site: the App Connector, the App Connector Group it belongs to, the Private App that is published through the group, and the Private Access Policy that decides who may reach it. Confirm the App Connectors screens and Socket v26.0.23570+ on the tenant before the call, and be plain in the room that Private Access is for user-initiated access only; the depth page carries the full boundary list.

The five-minute story

Bridge in, three beats, bridge out

Bridge in — from ZTNA

“That user reached an application on a Cato-connected site. What about the applications you do not want to on-ramp a whole network for?”

  1. Beat 1 — The connector that dials out

    Say: “This is the whole network change: one connector, placed beside the application, that opens an outbound DTLS tunnel to the best available PoP. It accepts nothing inbound and advertises no routes — the acquired data centre keeps its addressing and the firewall team keeps its weekend.”

    Show: Access → App Connectors — the Overview widgets (Connectivity Status, Model, Socket versions, App Connector Groups), then the one connected connector in the list: its group, model, connected PoP and the Private Apps it serves.

  2. Beat 2 — The application as a published name

    Say: “The user never learns an internal address. The app has an internal address the connector resolves locally, and a published domain the user types — the two can differ — and it is published through a connector group, not a single box, so a failed connector is not a failed application.”

    Show: Access → Private Apps — one app: Internal App Address against Published App Domain (app.example.intranet), the Service / Port items, Publish via the App Connectors Group, and the probing status that says it is available.

  3. Beat 3 — The rule, and what the user sees

    Say: “One rule: the group, the device posture profile and this app, Allow. No rule matches, access is blocked — the authorised user resolves and opens the name, and an unauthorised user's lookup simply does not resolve. The application is invisible, not merely refused.”

    Show: Access → Private Access → Private Access Policy — the allow rule and the empty space beneath it. Then the user experience: Marcus on the Cato Client opens app.example.intranet; for a user outside the rule, Cato DNS denies the lookup and the name does not resolve.

What the engine does

The PoP brokers; DNS is the gate; the connector forwards

The flow has four steps. The user connects to the Cato Cloud with the Cato Client or clientless access. The PoP authenticates the user and evaluates the Private Access Policy. If the user is authorised, the session is brokered through an outbound DTLS tunnel to an App Connector. The connector forwards the traffic locally to the application. The gate sits at DNS: when the user looks up the published domain, Cato DNS returns a synthetic (CGNAT) IP for an authorised user and denies the request for everyone else — the domain does not resolve and no session to the application environment is ever established. Authorisation is decided at the PoP before any session reaches the application, and once access is granted the traffic is subject to Cato's full security stack, including Threat Prevention and CASB/DLP inspection.

🚪

No network change

Private Access requires no inbound firewall rules, uses outbound-only tunnels from the application environment, does not require IP readdressing and does not require site on-ramping.

🫥

Invisible until allowed

The PoP assigns a synthetic IP to the published domain, so the user never learns the internal address. For an unauthorised user the domain does not resolve — the application is hidden, not merely refused.

🧩

Groups, not boxes

A Private App is attached to an App Connector Group of up to 10 connectors. The PoP probes them continuously, selects the optimal one per session and fails over automatically with no administrator action.

🧭

Same engine, same policy objects

The rule uses the IdP-synced groups and the Device Posture Profiles already defined across the account. Once a session is granted, the full security stack — Threat Prevention, CASB and DLP — still inspects it.

Demo runbook

Five minutes, three screens and one lookup

  1. The connector that dials out 1 min

    Access → App Connectors

    Say: “This is the only thing we deployed in the acquired data centre — a connector, physical X1500 or a virtual image in AWS, Azure, GCP or ESXi, that opens an outbound DTLS tunnel. No inbound rule, no route advertisement, no readdressing.”

    Show: The Overview widgets — Connectivity Status, Model, Socket versions, App Connector Groups — then the one connected connector in the list: Name, Connectivity Status, Group, Model, Country, Connected PoP and the Private Apps column. Use the Group by drop-down to show which connectors sit in which group and which apps the group covers.

  2. The application as a published name 1 min

    Access → Private Apps

    Say: “Two names: the internal address, which the connector resolves on its own LAN, and the published domain, which is all the user ever sees. It is published through the connector group, not a single connector, and only the ports we list are allowed.”

    Show: One app opened: Internal App Address beside Published App Domain (app.example.intranet), the Service / Port items (for example TCP/443), Publish via the App Connectors Group with the group selected, and the probing status showing the application available through the group.

  3. The rule that allows; the default that blocks 2 min

    Access → Private Access → Private Access Policy

    Say: “Who, under what conditions, to which app. Users and groups come from your IdP; the criteria can require a Device Posture Profile, a platform, the Client as origin, a country or a user risk level — all of them must hold. Rules are evaluated top down, first match wins, and if nothing matches, access is blocked. Every match generates an event, and that is the hit count.”

    Show: The one allow rule — Finance group, the corporate Device Posture Profile as criteria, the Private App, action Allow — and the absence of anything beneath it. Point at the Hit Count column as the evidence that the rule is doing work.

  4. What the user sees 1 min

    Cato Client device → browser / terminal

    Say: “Marcus types the name and it opens: Cato DNS answered with a synthetic IP, the PoP stitched his session through the connector's outbound tunnel. The contractor types the same name and gets nothing — Cato DNS denies the lookup and the name does not resolve. You cannot attack what you cannot resolve.”

    Show: From a Cato Client device in the Finance group, open app.example.intranet in the browser. From a device whose user matches no rule, run a lookup for the same name and show that it does not resolve. If you have only one device to hand, narrate the second outcome from the reference architecture rather than faking it.

Transition. Say it before you change screen: “Every one of those flows produces telemetry, and that telemetry answers the question you will hear most: is it slow because of Cato?” Then open Segment 7: Digital Experience Monitoring.

Likely questions and the two-sentence answer

“Is this generally available today?”

The KB pages no longer carry the request-enablement note they had until mid-October 2026, but connectors still need Socket v26.0.23570 or higher (Support provides it if the account lacks it). Confirm the App Connectors and Private Apps screens and that Socket version on the customer's account as the first PoV action rather than a surprise later.

Private Access with App Connectors — status and scope

“Can the application call back to the user, or sync to another site?”

No — Private Access supports user-initiated access only; applications do not initiate connections toward users, and server-initiated or bidirectional patterns are out of scope. Those scenarios are served by the full Cato networking architecture of Socket and IPsec sites, and an environment published through connectors today can be onboarded as a full site later if it needs them.

Private Access with App Connectors — the boundary

“We have overlapping IP ranges from an acquisition — does that matter?”

It is the case this was built for: the application is published without readdressing, because the PoP abstracts the internal address behind a synthetic IP from the account's CGNAT range and DNS mapping, and users reach it without routing-domain integration. The defaults are 100.64.0.0/16 for management and 100.65.0.0/16 for applications, and both can be overridden under Resource → System Settings if they clash.

Private Access with App Connectors — M&A and CGNAT

“What happens when a connector fails?”

The PoP stops selecting it for new sessions and routes subsequent sanctioned sessions through the next best connector in the group — automatically, with failover designed to restore access within 30 seconds, although some active sessions may need to be re-established. Deploy at least two connectors per group in separate availability zones, racks or power domains; a group holds up to 10.
