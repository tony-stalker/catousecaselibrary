What this shows

The journey, phase by phase

Every Zscaler replacement runs into the same fear: pull users off ZIA and internet security goes dark. It never has to. Cato builds the private-app rail first — a Socket into the London datacentre, a vSocket into AWS eu-west-2 — so the destinations users care about are already on the backbone before anyone moves. ZIA keeps protecting web traffic the whole time; the pilot only swings to the Cato PoP once the converted web policy is live and proven, and the fleet follows in waves. Throughout the transition ZCC and the Cato Client co-exist, so protection never has a gap.

Press play below and watch the estate change one element at a time — the branch, the remote user, the two app estates, the ZIA cloud and the Cato PoP hold their positions while the lanes between them move. Phase by phase

What happens each phase

The same five steps, in words. The right-hand column is the answer to the objection that stalls every SSE migration — where the user’s internet and private-app traffic is protected at each moment.

PhaseWhat changesUser traffic during this phase
0 · On Zscaler Starting state — site on GRE/IPsec to ZIA, ZCC on every endpoint; private apps in London DC and AWS eu-west-2 reached over ZPA and backhaul. No Cato yet. Internet: ZIA. Private apps: ZPA / backhaul into the DC and AWS.
1 · Rail first A Socket lands in London DC — the estate's anchor — and a vSocket in AWS eu-west-2: the private-app rail moves onto Cato WAN rules. The vSocket is the classic early, low-risk win. No user-facing change. Internet: ZIA, unchanged. Private apps: still ZPA / backhaul — the green rail is ready behind them.
2 · Pilot cutover The branch Socket and pilot Cato Clients swing to the PoP for private apps and converted SWG policy; ZCC rides inside the tunnel; interim IKEv2 IPsec keeps ZIA one flip away. Internet: Cato PoP for the pilot, ZIA for everyone else. Private apps: through the PoP to the DC Socket and AWS vSocket.
3 · Waves Remaining cohorts swap wave by wave with the same dual-agent bridge; ZIA drains — its egress, the ZPA lanes and the fallback all drop to standby. Internet: Cato PoP. Private apps: Cato. ZIA held as a dormant fallback only.
4 · ZIA / ZCC retired ZCC uninstalled, ZIA and ZPA decommissioned. Site, users and both app estates fully on Cato. Cato PoP — one client, one platform for internet and private apps.
Why there is never a gap

The dual-agent bridge

The mechanic that removes the risk is co-existence — and sequencing. The private-app rail moves first: once the London DC Socket and the AWS vSocket are up, the destinations are on Cato before any user is, so the user cutover is only ever about where web policy is enforced. Through the transition (phases 1–3) ZCC and the Cato Client run side by side on the same endpoint. On-site the ZCC tunnel rides inside the Cato socket tunnel; when remote, the ZCC and Cato SDP tunnels co-exist on the workstation. Internet security stays enforced by ZIA for every unmigrated cohort — right up to the moment the converted Cato policy is proven and that cohort's web egress flips from ZIA to the Cato PoP.

The one line that beats the objection

“Internet security never goes dark. The private apps move first — Socket in the DC, vSocket in AWS — then users swing cohort by cohort, with ZIA kept one flip away over interim IPsec until Cato’s converted policy is live and proven. Only then does ZCC come off. Every phase is independently reversible.” The full four-phase policy conversion behind that flip is in the Zscaler (ZIA / ZPA) to Cato use case.
