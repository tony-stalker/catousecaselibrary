Private Access with App Connectors

A VPN gives a user the network; Cato Private Access gives them the application. It is a user-to-application service brokered at the PoP — distinct from on-ramping a site — in which an outbound-only App Connector next to the application publishes it under a domain that only resolves for users the Private Access Policy allows. No inbound firewall rules, no route advertisement, no readdressing: this use case shows how to publish a private application without touching the network, and when a full Socket or IPsec site is still the right answer.

Business objective

Why this matters

Every private-application access project runs into the same wall: to reach an app, a user has traditionally had to be put on the network that hosts it. That means a VPN concentrator with inbound rules, subnets advertised into a routing domain, and — in any estate with more than one history — IP ranges that collide. The application project becomes a WAN project, and the WAN project takes a year.

Cato Private Access breaks that dependency. As the KB puts it, it lets you "provide secure, identity-based access to private applications without extending your network to users": instead of network-level connectivity, you enforce least-privileged, application-specific access on user identity and context. Applications stay hidden and unreachable unless a policy explicitly allows them, sessions are brokered through outbound-only App Connectors, and the whole thing goes in "without modifying WAN topology or IP addressing".

The objective for the SE: publish one real internal application to one real user group, in the customer's own cloud or datacentre, without a single change to their routing, firewall ingress or address plan — and show the deny as clearly as the allow.

Where it fits

When a site is the wrong tool

Cato's ZTNA broker supports two deployment models under one policy engine: private access via sites (Socket, vSocket or IPsec — the site provides access to everything behind it) and private access via App Connectors, where "application access is enforced in the Cato Cloud rather than being dependent on underlying network topology". Four situations where the connector model wins outright:

M&A with overlapping IPs

The acquired estate uses the same 10.0.0.0/8 slices you do. Private Access "publishes applications without requiring IP readdressing, abstracts internal addressing using CGNAT and DNS mapping, and allows user access without routing-domain integration". Day-one access to their HR and finance apps while the network integration runs on its own timeline.

Partner-hosted or isolated apps

An application lives in a network you do not own or cannot route into — a managed-service provider's hosting, a lab segment, a brownfield site. A connector inside that environment needs only outbound internet; the host network never has to accept an inbound rule or learn a route.

Cloud VPCs you cannot re-address

A VPC built by a product team with its own CIDR plan, no transit gateway, no appetite for a vSocket redesign. Deploy the connector image from the AWS, Azure or GCP Marketplace into that VPC or VNet and publish the app. "Independent routing domains for each private network — no requirement for unique IP spaces."

Quick wins before the WAN project

The KB frames Private Access as "designed for rapid deployment and incremental adoption". Publish the three applications the remote workforce complains about most, prove ZTNA quickly, and let the socket rollout follow at its own pace — the policy you write now carries forward.

Be honest about scope — user-initiated only

Private Access "supports user-initiated access only. Applications do not initiate connections toward users, and server-initiated or bidirectional communication patterns are not supported." Site-to-site replication, a management server that pushes to agents, a build system that calls back into developer workstations — those "fall outside the scope of Private Access and are supported by the full Cato networking architecture of IPsec and Socket sites". The KB's own M&A guidance is the right line: start with Private Access; "if bidirectional or server-initiated connectivity is required later, you can onboard the environment as a full Cato site."

Discovery question

"Which application have you been asked to give people access to that is still waiting on a network change — a firewall rule, a route, a re-addressing — and how long has it been waiting?"

The Cato solution

Brokered at the PoP, published by the connector

The Cato PoP is the ZTNA broker. It registers each published application in the Private Access control plane and assigns it a synthetic (CGNAT) IP that stands in for the application, so users never learn or connect to the internal address. Authorisation — identity, policy, application, port and protocol — happens at the PoP before any session to the application environment exists: "unauthorized application requests are denied before a session to the application environment is established." Once a session is allowed, it is still subject to Cato's full security stack, including Threat Prevention and CASB/DLP inspection.

DTLS tunnel, held open outbound by the connectorConnector to app on the LANClient or browser to the PoPLive traffic
Faded boxes are the second connector in each group: the PoP probes every connector, picks the best one per session, and moves new sessions to the next best one if the current one becomes unreachable. Browser access covers HTTP(S), RDP and SSH apps; other protocols need the Cato Client.

The flow, step by step

  1. User connects to the Cato Cloud

    Through the Cato Client or another supported access method. User devices use the Cato DNS service at 10.254.254.1 so that queries for published domains reach the PoP.

  2. DNS request for the published domain

    Priya's device asks for app.example.intranet. The PoP identifies the Private App behind that domain and evaluates the Private Access Policy — identity, criteria, and whether the application, port and protocol are authorised.

  3. Allow: synthetic IP returned. Block: no answer.

    "If the user is authorized, Cato DNS returns the synthetic (CGNAT) IP address assigned to the published application domain. If the user is not authorized, Cato DNS denies the request. The domain does not resolve, and no session to the application environment is established."

  4. Session stitched through the connector

    Priya connects to the synthetic IP; the Cato Cloud sanctions the session, selects the optimal App Connector from the group and stitches the session into the outbound DTLS tunnel that connector already holds open.

  5. Connector forwards on the LAN

    The connector resolves the configured internal destination through its internal DNS when required and forwards the traffic over the local network. Priya communicates only with the synthetic IP; she "does not receive direct network reachability to the application environment".

🙈

Hidden until authorised

The published domain is only available to users the policy allows; everyone else gets no DNS answer. The internal address is never exposed — users only ever see the synthetic IP.

🔌

No network change

Outbound-only tunnels from the application side: no inbound firewall rules, no advertised subnets, no readdressing, no site on-ramping. The connector gets its LAN address, gateway and DNS by DHCP.

🪪

Identity and posture at the PoP

Rules combine IdP users and groups with device posture profiles, platform, country, origin and user risk, continuously evaluated per session request.

🔁

Resilient by group

Two or more connectors per group across zones or racks; the PoP probes them and fails new sessions over automatically, with no administrator action.

Design guidance

Designing it properly

Groups and resilience

  • One group per environment, region or security zone — production, DR, cloud, on-premises. The group an app publishes through must contain at least one connector that reaches the app over the LAN.
  • At least two connectors per group, each able to reach the same destinations. Cloud: separate availability zones or regions. Physical: separate racks, power domains or failure zones.
  • Up to 10 connectors per group; each app publishes through one group at a time.
  • Failover is automatic and "designed to restore application access within 30 seconds" — existing sessions may need to re-establish, depending on the protocol.
  • Multi-region apps: a connector in each environment that hosts an instance, all in the group the app publishes through.

DNS and addressing

  • User side: Cato DNS at 10.254.254.1 processes published-domain queries at the PoP.
  • Connector side: DHCP for LAN IP, gateway and internal DNS; an internal FQDN in a Private App must be resolvable by that DNS. Static LAN IP and DNS is listed as "Coming Soon".
  • Reserved ranges: MGMT 100.64.0.0/16 (reserved once a connector is deployed) and Application 100.65.0.0/16 (reserved once an app is published). If either collides with the customer's network, override them under Resource → System Settings.
  • Probing is ICMP today (interval and fault threshold configurable); if the app cannot answer ICMP, disable probing for it — and accept you lose connectivity and performance monitoring for that app in the CMA. TCP probes are promised for the future.

Availability — check the tenant before you promise

Until mid-October 2026 the core Private Access and App Connector KB pages (What Is Cato Private Access, Working with App Connectors, Monitoring App Connectors, Configuring Private Applications, Configuring the Private Access Policy) carried a request-enablement note pointing to feature-releases@catonetworks.com; their 14 Oct 2026 revisions no longer do. The Socket prerequisite stands: connectors need Socket v26.0.23570 or higher, and if the account does not have it the KB says to ask Support to provide it. Confirm the App Connectors and Private Apps screens are present on the tenant, and that version is available to the account, before a demo or PoV date is agreed.

Licensing (Base Products): sites "are licensed based on bandwidth and support all site types, including physical sites (Sockets), IPsec, Cloud Interconnect, and App Connector deployments". The Bandwidth Pool covers "App Connector deployments for private application access, with no limitation on the number of App Connectors or published applications", and includes private-application traffic via App Connector in its P95 measurement. Remote users need ZTNA User licences (each account gets 5 free by default; they do not apply to users connected through a Cato site). Whether a connector consumes anything beyond pooled bandwidth is not stated in the KB — ask rather than assume.

Demo runbook

How to run the demo

Before you demo

Have one Private App already published through a group with two connected connectors, one Allow rule for a pilot group, and two test identities: Priya (in the group, compliant device) and Marcus (not in the group). The whole demo is the contrast between their two DNS lookups. Confirm the App Connectors screens are present on the demo tenant first — see Availability above.

  1. Start at the connector estate

    Access → App Connectors

    The Overview widgets: Connectivity Status (connected, disconnected, degraded, disabled), Model (X1500, AWS, Azure, GCP…), Socket versions, and App Connector Groups with the number of apps on each. Use Group by to show which connectors sit in which group and which apps each group carries. Point at the Connected PoP column: "this box in their AWS VPC dialled out to a PoP — nothing dialled in."

  2. Open one connector's analytics

    Access → App Connectors → select connector → Network Analytics

    Site & Tunnels tab: Connector Status, average upstream/downstream throughput, packet loss and discards. Hardware tab: average CPU and per-core load. This is Socket-style telemetry in the same Network Analytics view — the connector is Socket software, not a black box.

  3. Show what is published

    Access → Private Apps

    Open the app: Internal App Address (the real host or IP, resolvable only inside the VPC) beside the Published App Domain (app.example.intranet) users will type. Show the service/port items limited to what the app needs, the group it publishes through, and the ICMP probe settings that drive the app's availability status. Mention that the page also flags Private Apps defined but not yet referenced by any policy rule.

  4. Show who gets it

    Access → Private Access → Private Access Policy

    One rule: Users / Groups = the pilot IdP group; Criteria = a Device Posture profile (for example anti-virus up to date) and Platform = Windows; Private Apps = the published app; Action = Allow. Walk the rest of the criteria set — user risk level, origin (Client only), country — and the default: "if no rule matches, access is blocked." Point out revisions and the Hit Count column.

  5. Live proof: two lookups

    As Priya, on the Cato Client: resolve app.example.intranet — it answers with a 100.65.x.x address — then open the app. As Marcus, same command: the name does not resolve. Nothing was blocked at a firewall; Marcus's device never learned where the app is. Then stop one connector (or disable it) and repeat Priya's test — new sessions move to the other connector in the group.

  6. Close on the evidence

    Monitor → Events

    Filter to the pilot rule: Private Access Policy rules generate an event on every match and the rule's Hit Count is derived from them. Priya's allowed sessions, attributed to her identity and the rule name, are the audit trail; the absence of any session for Marcus is the point.

Prerequisites — agree before week one
  • Feature present and Socket version available. Confirm the App Connectors and Private Apps screens are on the customer's tenant and that Socket v26.0.23570+ is available to the account (Support provides it if not) before the kick-off date is set.
  • An IdP. "Private Access requires authenticated user identity, and unauthenticated users can't access private applications." The pilot group exists in the IdP and syncs to Cato — design choices in Identity Integration Design.
  • One application, written down. Internal address, published domain, the exact services and ports, and the environment it lives in. The destination must accept inbound traffic from the connector on the LAN; an internal FQDN must resolve through the DNS the connector gets from DHCP.
  • Somewhere to put two connectors. A VPC with three /28 subnets (or two for Azure 2-NIC), an ESXi 8.0 host, or two X1500s — in separate zones or racks — with outbound internet. A DHCP-served LAN for the connector's address and DNS.
  • Licences. Bandwidth Pool for the connector traffic; ZTNA User licences for the pilot cohort (five are free by default).
  • Address check. Confirm 100.64.0.0/16 and 100.65.0.0/16 are unused in the customer's estate, or agree the override values up front.
  • Devices on the Cato Client with DNS pointed at 10.254.254.1. Browser-based access is in scope only if the app is HTTP(S), RDP or SSH.

Configuration walkthrough

  1. Create the connector objects and the group

    Access → App Connector → New

    For each connector: name, country, Type (Physical or Virtual), Connector Group (type a new name to create it — one group for this environment), Preferred PoPs left at Disabled unless the customer wants them pinned. Apply, then copy the serial number for virtual connectors (Working with App Connectors).

  2. Deploy the two connectors in the hosting environment

    Access → App Connectors

    AWS: Marketplace image into the VPC with MGMT/WAN/LAN subnets, IMDSv2, serial number pasted, then reboot to initiate the connection (Creating App Connectors in AWS). Azure (guide), GCP (guide) and ESXi (guide) follow the same shape. Physical X1500: cable it, then assign it from Notifications → Activate New Socket → Assign to: App Connector (Creating Physical App Connectors). Do not go further until both show Connected with a Connected PoP.

  3. Publish the application

    Access → Private Apps → New

    General: name. App Settings: Internal App Address and Published App Domain (same or different), Service / Port items limited to what the app needs. Publish: Enabled, via App Connectors Group, the pilot group. Probing: default ICMP interval and fault threshold, or disabled if the app will not answer ICMP. Apply; status should show available, not Disabled (Configuring Private Applications).

  4. Write the Allow rule — and nothing else

    Access → Private Access → Private Access Policy

    New → New Rule: Users / Groups = pilot IdP group; Criteria = the customer's existing Device Posture profile, the platforms the cohort actually uses, origin Client; Private Apps = the pilot app; Action Allow; Track: Send Notification if the customer wants alerts. Save, then Publish. There is no discovery-rule week here: the policy's default is block, and the control user's failed lookup is evidence from day one (Configuring the Private Access Policy).

  5. Run the paired tests and the failover

    Monitor → Events

    Pilot user: lookup resolves to 100.65.x.x, app opens. Control user: no answer. Same pilot user with the posture check deliberately failed: no answer. Then stop connector A in the hosting environment, note the time the list shows Disconnected, re-run the pilot user's test through connector B and record the time to restore against the KB's "designed to restore application access within 30 seconds". Bring A back and confirm the group shows both Connected.

  6. Assemble the evidence pack

    Monitor → Events Access → App Connectors

    Export events filtered to the pilot rule for the period; screenshot the rule's Hit Count; screenshot the connector list during and after the failover; attach the customer's own change record showing no firewall, routing or addressing change in the hosting environment.

What good output looks like

Four screens tell the story: the connector list with both pilot connectors Connected to a named PoP; the Private App showing available through the group; the policy rule with a climbing Hit Count; and the events view filtered to that rule, every row carrying the pilot user's identity. Beside them, two terminal captures — one lookup answering 100.65.x.x and one not answering at all.

Troubleshooting the pilot

🔌

App shows Disabled

No connector in its group is connected — the KB is explicit that the app "appears as disabled" until one is. Check Access → App Connectors: Connected PoP empty means it never reached Cato (WAN subnet, outbound internet, serial number); a last-known PoP means it dropped. Deploy and connect before publishing.

🧭

Pilot user resolves, but the app does not open

The connector cannot resolve or reach the internal destination. An internal FQDN must resolve through the DNS the connector obtained by DHCP, and the destination must accept inbound traffic from the connector on the LAN. On Socket v26 the app must sit in the connector's LAN subnet.

📡

App flaps Unavailable with no user impact

The application does not answer ICMP, so the probe trips the fault threshold. Disable probing for that Private App (TCP probes are not yet available) and note that CMA connectivity monitoring for it goes with it.

🧮

Odd routing after publishing

100.64.0.0/16 or 100.65.0.0/16 was already in use somewhere in the estate. Override the management and application ranges under Resource → System Settings and re-test the lookups.

🧩

Published, connected, still no answer for the pilot user

Work the policy: is the user in the synced IdP group under Access → Users, do all the rule's criteria match (they are ANDed — posture, platform, origin, country), and is the app assigned to the group the rule and the app both reference? Remember the policy must be Published, not just Saved.

🧱

Everyone is blocked

That is the design: "if no rule matches, access is blocked." A rule order problem (a Block above the Allow) or a rule scoped to the wrong group looks identical from the client. Check Hit Count on each rule to see which one is matching.

Gotchas & exit

Say these out loud before week one
  • Tenant readiness. If the tenant does not show App Connectors, or the account cannot get Socket v26.0.23570+, the PoV does not start. Confirm both first, then book the kick-off.
  • User-initiated only. If the pilot app needs to call back to the user's device, or another server needs to reach it, that app is a site use case — pick a different app or scope a site.
  • Lowest network priority, no QoS. Do not pick a voice or video workload to prove Private Access with.
  • Failover re-establishes sessions. "Within 30 seconds" is a design target for new sessions; a long-lived session may need to reconnect. Measure and quote what you saw.
  • Browser access is HTTP(S), RDP and SSH only. Any other protocol means the pilot cohort is on the Cato Client.

Unwinding cleanly: disable the pilot rule rather than delete it — its Hit Count and events are the record; set the Private App to not published; leave the connectors in place if a rollout is likely (they become the first production group; confirm with Cato whether idle connectors carry any licence implication), or delete the connector objects and tear down the VMs if not; revert any CGNAT override you made for the pilot. If the answer is yes, the pilot group, app and rule are the production rollout's first application, already live.
